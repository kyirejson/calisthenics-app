# 拍照记餐升级（本地开发）

日期：2026-09-29。没有上传代码、发布 APK 或部署公网服务。

## 操作方式

今日 → 饮食 → 拍照记餐。拍照/相册自动区分包装标签和普通餐食；同一入口也可直接拍营养标签或扫商品条码。

三种模式现已共用同一取景区、快门和相册，切换不再打开独立标签／条码相机弹窗；手动建库也复用此组件。详见[统一相机与验收](nutrition-unified-camera-2026-09-29.md)。

- 包装：核对识别出的原始能量、单位、蛋白质、碳水、脂肪、生熟状态与过敏原，明确保存至个人食品库，再选择实际吃下的份量。
- 净重清楚：提供整包、半包、四分之一包。净重未知时只提供注明克重的参考量和手填重量，绝不把每100g计量基准当作整袋或一份。
- 普通餐食：严格采用已确认的三步 UI：拍照记餐 → 核对食材 → 确认这一餐。AI只输出食材候选、原料状态、参考克重/个数，不再直接给整道菜热量。
- 第二步提供个数增减、少油/普通/多油（5/10/15g）及无油选择、全部/一半/四分之一。油量初始未选，必须由用户确认；克重、生熟状态、替换和移除收进“调整克重与配料”。漏掉的配料可补充。未匹配食材、状态歧义和未知份量不会被悄悄套成其他食品或100g。
- 第三步展示实际照片、数据库计算后的能量/宏量营养、可展开的逐项来源与克重，再选择餐次保存；可返回第二步重新计算。无网络发送同意不识图；点击“按食材计算”不记餐，必须再确认记录。
- 可选勾选“保存照片到本机”，默认不选。已保存照片在餐次列表/记录详情中可查看。
- 编辑照片记录可补拍标签修正单项；“保存并应用这项更正”明确提交当前记录，保留原 ID、创建时间和未被选中的其他食物，不制造一条重复记录。

## 计算与数据真实性

AI负责读取/结构化，不负责计算已核对标签或拆解食材的最终摄入。客户端按 `kcal = kJ / 4.184`、`摄入营养 = 每100g营养 × 所选克重 / 100` 计算并保存独立快照。每项计算份量先按吃下比例换算，克重与营养保留一位小数。

番茄炒鸡蛋示例：2个大鸡蛋按去壳生蛋液100.6g（USDA参考量），2个番茄按250g（开发者方便估量，并非USDA番茄个数实测），10g芥花籽油参考，共284.8kcal。成品照片看不见的原料重量和实际油量仍不准确，按库计算≠称重实测；也不能假设所有菜籽油和番茄品种都等同该参考条目。调整原料、品种或油种可改变结果。设计图276kcal未写入程序。

盐焗腰果示例：标签每100g 2515kJ、蛋白质23g → 601.1kcal/100g；选择30g → 180.3kcal、蛋白质6.9g。这个例子不能证明用户真的吃了30g。缺失脂肪、碳水不能由名称或4/4/9补造，必须补拍/手动核对；未标纤维保持“未知”，不显示为已知0g。

历史记录没有克重/照片时，不反推重量、不填默认100g、不补造旧照片。个人食品修改或删除不会改变已保存摄入快照。标签计算、食材计算与旧视觉估算分别标注；食材计算仍带份量不确定性，不冒充称重数据。新记录保存dishName和calculation=ingredients以及每项数据/来源版本，重开后不调用模型重算历史。

## 照片存储与删除

- Web：当前来源的 IndexedDB，数据库 `uncover-nutrition-photos-v1`，独立 JPEG Blob。
- Android/iOS：应用私有 document/nutrition-photos 目录，不上传公共食品库。保存的是经过压缩的JPEG，不是原始无损照片。
- 饮食 JSON 只存受限、不透明的照片 ID、类型与拍摄时间，不放 Base64/外部网址/任意文件路径。一条记录最多3张。
- 先保存照片，后持久化饮食记录；后者失败只回滚本次新照片。删照片引用、删记录、清除应用数据均先成功保存记录变更，再清理不再被记录或收藏使用的文件。
- 历史编辑中“移除照片”后需要保存更正；仍被收藏引用的照片不删除。
- 本机存储不等于永久云备份。卸载、清浏览器数据、更换设备或来源/端口可能使照片不可用，营养快照仍可独立存在。当前数据导出仍是JSON，只含照片引用，**不包含照片文件**。
- 在传统手动记餐编辑器里导入食品标签，仍不自动保存标签照片；可明确选择“保存本次包装照片”，将其留作个人食品配图。也可上传个人食品照片，下次选食品时复用。见[食品图片升级](nutrition-food-artwork-2026-09-29.md)。

## 服务改动

继续复用 `/v1/nutrition/analyze-photo`，一次模型调用自动分流。

- 包装响应：`{kind:'label',draft:FoodLabelDraft}`，由服务端赋予受控来源。没有清晰营养表时字段为null，要求补拍，不回退成通用食物估值。
- 普通餐食：返回食材候选契约，不返回整菜营养。精确名称/别名加生熟条件匹配库，未知/冲突需人工选择。保存时才生成带逐项catalog来源的PhotoEstimate；旧PhotoEstimate仍可读取/编辑，不作为新识图接口的兼容回退。
- 图片2048长边压缩、模型 high detail。高分辨率不是准确率保证。已删除连续识图、即时热量叠加及自动刷新代码；相机页不展示尚未确认的热量。离开应用中止识别并停相机，返回后需要手动操作。
- 条码仍通过 Open Food Facts 只读查询，不调用 DeepSeek；查询结果须核对。未能获得净重时保持未知，不从营养列/每份克重推算。
- 服务仍仅监听本机，密钥只保存在服务端，不写进客户端；未扩大公网权限。

## 验收与边界

营养侧146项、服务侧82项测试通过，包含候选契约、拒绝模型营养猜值与重复食材、未知/歧义匹配、显式用油、真实数据库计算、比例变化、个人食品和快照重载，以及腰果kJ换算、单项补拍更正、照片回滚等既有逻辑。

隔离浏览器320/390/650/1280px覆盖：自动标签识别、强制核对、30g换算、照片默认不存、选存、IndexedDB保存失败回滚、刷新回看、缩略图不误触餐次弹窗、删除记录清文件、旧记录补拍纠正。使用合成图片与模拟响应，未访问用户的浏览器数据、未向真实AI发送照片或产生费用。

同尺寸新增三步食材流程验收：数量/用油/吃下一半改变计算、来源依据、返回修改、不自动记餐、未匹配食品阻止计算、选库恢复、记录失败及重载。`scripts/smoke-ingredient-camera.cjs`使用合成番茄图片和固定“番茄炒鸡蛋”响应，只验证UI/流程，不代表照片识别准确率。

初版三个原图为`assets/nutrition-ingredients/egg.png`、`tomato.png`、`oil.png`。现已扩展为共享食品图片机制，运行时统一使用`assets/nutrition-foods/`的13张320px压缩缩略图，覆盖101项食品的食材/分类配图。用户菜肴顶部仍是本次拍摄图片；配图不作为数量或营养数据来源。提示词与模式见[素材提示词](nutrition-ingredient-artwork.md)。

还未完成：Android真机照片权限/私有文件生命周期验收、端侧OCR、焦距/反光/模糊的自动质量检测、云备份/照片随导出打包、真实食品/标签识别基准集和误差统计。不能声称“拍照精确测出热量”，不能承诺AI会无误分流或抄录；用户核对仍是必要步骤。
