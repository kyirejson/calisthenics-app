# BLACK Agent 语音交互重构方案

日期：2026-10-15；状态：用户已批准，正在实施；实际进展与未完成项见 `voice-refactor-progress-2026-10-15.md`。项目基线：`95a43f1c8c3c582e79b07864c55253b17eadf9ce`（v1.7.17）。

本方案取代此前“现有音频组件默认保留、先叠加声纹限制”的规划判断，但不改写历史版本的实现记录。用户批准后开始修改 App 代码；不接入未经批准的新云服务，不把开发回归当作正式发布验收。

实施约束更新：语音对话只用 App 内置中文合成，不保留手机系统 TTS 的自动或显式备用。目标手机为 OPPO Find X8 Pro / ColorOS 16.0.10；具体性能与声学效果以该机验收为准。

## 1. 决策摘要

1. **重做整个语音子系统的职责与接口，不重写训练、饮食、音乐等业务。** 采集、AEC、播放等旧实现均重新验收，不因已存在而默认合格。
2. **专属声纹退出本轮产品与技术路径。** 不登记、不验证、不用“主人认证”作为唤醒、转写或打断条件；也不继续给模型传 `ownerVerified:true`。
3. **参考豆包的分层与交互原则，不声称照搬其完整私有架构。** 采用持续收音、上/下行独立状态、统一会话控制、语音与语义共同判断轮次；不把“检测到声音”当成“用户要求打断”。
4. **现有 DeepSeek 业务 Agent 和已授权工具继续使用。** 不用关键词分配音乐/饮食意图，不用声学层删除模型工具，不为了简短截断模型必要回答。
5. **先做可验证的语音基础，再提升自然度。** 第一阶段采用可控的流式级联链路；若要达到原生全双工模型的语调理解和抗干扰水平，还要完成模型层能力升级，不能把客户端阶段验收冒充最终等效。
6. **不默认开通豆包、火山或其他付费服务。** 新增云音频处理、服务器或服务费用需另行确认；本文给出接入边界，不偷偷切换供应商。
7. **以真实对话结果交付。** 单元测试、编译、模拟器均不能替代 ColorOS 手机的外放连续对话验收。

## 2. 本轮目标与排除项

### 2.1 必须达到的用户体验

- 开启后不必先发文字，首次就能进入正常语音会话。
- 单喊 BLACK，由 Agent 回答一次“我在”；BLACK 后直接跟请求则直接处理，不插入多余问候。
- 一次唤醒后可连续交流，不必每句话重新喊名字；有明确的结束与静音入口。
- 助手生成时展示文字，开始出声不必等完整长回答结束；播报进度与实际声音对应。
- 用户正常停顿、思考、修正时不被机械拆成多次请求。
- 外放时不因自己的回声触发新对话；用户真正插话时停止旧回答并听完整新请求。
- 噪声或短暂无关声音不会把长回答永久丢弃。
- 播放失败与用户打断分开提示，文字和已完成工具结果保留，不重复写饮食或重复播放音乐操作。
- 回答简洁自然；复杂问题仍可按用户要求详细解释。
- 前台、后台、锁屏、切换输出设备的行为清楚、可观测；系统不允许时如实说明。

### 2.2 不包含

- 专属身份、声纹登记、说话人白名单、声纹克隆或活体鉴别。
- 视频通话、摄像头理解、主动陪伴等扩展功能。
- 绕过 Android 强行停止、麦克风权限或系统后台限制。
- 复制豆包私有服务、提取其账户令牌、复用其闭源模型权重或商业音色。
- 重做跑步、训练报数和公里播报；只协调它们与 Agent 的音频焦点，避免互相破坏。

### 3.2 从豆包借鉴的架构原则

- 收音和说话可同时进行，不用一个 speaking/listening 互斥开关表达全部状态。
- 声学处理负责降低回声与噪声；模型负责理解表达和交互意图，二者不能互相替代。
- “人声存在”“用户说完”“正在对助手说话”“要求打断”是不同问题。
- 连接与设备生命周期独立于业务推理；音频故障不应重跑业务操作。

以上是基于公开材料和客户端证据形成的设计归纳，不是声称取得豆包内部设计文档。

## 5. 推荐技术路线与模型边界

### 5.1 默认实施路线：可控的流式语音链路

本地 KWS / 音频前端 / 流式 ASR → 轮次与交互判断 → 现有业务 Agent → 增量中文合成 → 连续 PCM 播放。

- 适配现有 Expo + React Native + Kotlin + C++，不要求重写 App。
- 不新增付费账户；业务推理继续用用户已配置模型。
- 不把当前系统 TTS 更换一次音色当作解决方案；评估独立可控的本地中文合成。
- 这是全双工音频工程链路，但不是原生端到端语音模型，验收必须使用准确名称。

### 5.2 最终自然交互目标：有声学理解能力的模型

若阶段一在慢速表达、旁人干扰或交互指向性上仍达不到目标，不能再无限叠加音量/静音规则；进入原生音频模型评估。

必要能力：持续输入音频、同时输出、音频/文字对应、可取消且不复活旧音频、能表达倾听决策、可连接工具与回执。只支持“整段上传后回答”的模型不算满足。

接入方式必须二选一并在会话建立时固定：

1. 音频模型作为会话主体，经统一 ToolExecutor 使用现有工具；文字聊天和语音的模型选择与能力差异必须明确告知。
2. 音频模型只承担听说/轮次，业务请求交给现有 Agent；由后者拥有唯一工具执行权。需要测量双模型往返延迟，不能双方同时执行。

当前推荐先做路线一的基础工程，再以真实语料决定模型升级；不在没有模型、许可、算力、预算和工具兼容证明时承诺“完全等同豆包”。原生路线是达成更高体验的独立里程碑，不是偷偷添加的商业依赖。

### 5.3 组件评估清单与选型门槛

| 能力 | 优先候选 | 需要现场确认 |
| --- | --- | --- |
| KWS | 现有 sherpa-onnx BLACK 模型先测，不合格再换 | 裸词/跟随请求、外放自唤醒、口音、功耗 |
| ASR | 现有流式 Zipformer 作为对照，不默认获选 | 中文纠错、英文歌名、首字丢失、实时率和线程占用 |
| AEC/NS/AGC | 可控 WebRTC APM 音频前端与系统处理对照 | 具体依赖编译体积、许可、路由兼容与双讲保真 |
| 本地合成 | sherpa-onnx 中文 Matcha、Kokoro 中英模型作为候选 [S6] | 机型实时率、首音延迟、长文稳定、包大小和音色授权 |
| 音频判停 | 调研 LiveKit 音频 turn detector 作为设计/评测对照 [S7] | 其 CPU 部署不等于 Android 可用；权重许可、ARM 推理和输入窗口必须单独验证 |
| 服务端合成 | 如需服务器，可评估 CosyVoice 双向流式 [S8] | 需要算力、网络、许可与费用；不是本轮默认依赖 |

P0 必须用候选原型跑出时延、内存、CPU、许可和体积清单，再固定版本与摘要。以上不是已经接入的组件，也不是默认把所有模型塞入 APK。若本地合成达不到手机预算，明确提交服务端方案供决定，不静默退回已失败的系统引擎并宣称完成。

## 6. 目标架构与职责

```text
麦克风 → CaptureDriver → AudioFrontEnd → KWS / StreamingRecognizer
                             ↑                    ↓
                       RenderReference       UtteranceDraft
                             ↑                    ↓
扬声器 ← StreamPlayer ← SpeechOutput ← AgentBridge ← TurnCoordinator
                         ↑          ↔ 现有会话、工具、持久化
                         └──── VoiceSessionController ────┘
                                   ↓
                           RN 界面 / 通知 / 诊断快照
```

这张图是拟建结构，不是声称豆包源码如此命名。

- **VoiceSessionController（Kotlin actor/reducer）**：唯一会话状态所有者，串行处理事件。只调用端口，不运行模型推理或写业务数据。
- **CaptureDriver**：唯一麦克风，采样时间戳、设备状态、重启和输入静音检测。
- **AudioFrontEnd**：参考对齐、AEC、降噪、必要增益；输出带质量信号的音频，不识别主人。
- **StreamingRecognizer / WakeDetector**：音频转写及唤醒证据，不决定业务意图。
- **TurnCoordinator**：草稿版本、判停、交互指向和打断候选；不执行业务工具。
- **AgentBridge（TS）**：加载配置和会话，调用原 Agent，投递文字/工具/发声事件，管理取消。
- **SpeechOutput**：模型或合成器产生音频；输出 PCM 与文本范围，不直接占用扬声器。
- **StreamPlayer / RenderReference**：持续播放与实际消费记录，给 AEC 提供时序一致的参考。
- **ConversationStore / ToolExecutor**：继续作为业务事实来源，不因语音重建另一套账本。

线程：采集线程仅读取与入有界队列；DSP 专用线程；ASR/KWS 工作队列；合成工作队列；播放器线程；会话事件串行队列。事件队列不搬运每个 PCM 帧到 JS。重模型不能堵塞 AudioRecord.read。

## 7. 会话状态与事件契约

### 7.1 三个正交维度

- 会话：Stopped / Starting / Ready / Suspended / Faulted / Stopping。
- 输入：WakeListening / Listening / SpeechCandidate / Collecting / Evaluating。
- 输出：Idle / Generating / Buffering / Playing / SoftHeld / Cancelled / Failed。

因此可以同时处于“输入 Collecting、输出 Playing”。UI 的“正在听/正在回答”是投影，不反过来控制引擎。

每个状态转换记录原因。麦克风不可用进入 Suspended，合成失败只改变输出；两者不得冒充 UserInterrupted。

### 7.2 事件身份

所有控制事件包含 `serviceEpoch, sessionId, turnId, eventId, sequence, monotonicTime`。按需附加 `draftRevision, generationId, segmentId, audioRouteEpoch, configRevision`。

- 服务重建更换 serviceEpoch，旧服务回调全部失效；不能用跨实例的单一 sequence 比较。
- 同一 utterance 草稿变化递增 draftRevision；旧判停不能提交新草稿。
- 同一回答重试合成不生成新的业务 turnId。
- 片段重复投递按 segmentId + sequence 幂等；sequence 的单调性只在指定事件域内成立。
- 取消粒度：cancelGeneration(turnId)、stopPlayback(turnId)、endSession(sessionId)、disableWake。禁止一个 cancel(null) 同时承担全部含义。

桥接端口拟为 startSession、endSession、submitAssessment、appendSpeech、finishSpeech、cancelOutput、snapshot、ackEvents。具体名称可在实现时统一，但语义不能合并。

Kotlin 与 JS 是不同职责的权威：前者拥有设备/音频会话，后者拥有对话/业务事实；通过版本化事件协调，不要求分布式同步原子状态。关键待办有界留存、确认后删除；新 JS 实例先取快照再续接事件，防止掉唤醒或重复工具执行。

## 8. 音频采集与 AEC 重构

### 8.1 音频采集

- 确定设备原生格式与能力，不把 16 kHz 支持当作所有路由的事实。优先稳定采集，必要时重采样供 ASR；帧结构携带采样率与时钟域。
- DSP 用固定 10 ms 帧；模型用各自窗口，使用有界 FIFO 衔接。记录缺帧、排队延迟和静音状态。
- 热路径复用缓冲，不反复分配整段数组；队列持续拥堵时明确报告过载并恢复，不能悄悄漏音。
- 输入中断、蓝牙切换、路由变更使 audioRouteEpoch 更新，重新校准时钟与前端，不能沿用旧参考延迟。

### 8.2 回声消除策略

必须做三组相同语料对照：系统处理为主；软件 APM 为主且尽可能避免重复系统处理；现有实现作为基准。双 AEC 叠加不是默认方案。Android 实际采集路径可能仍有厂商处理，必须记录可观测能力，不能谎称绝对原始麦克风。[S4]

- 不只验证回声变小，还要验证助手与用户同时说话时，用户声音没有被抹掉。
- 当前“相关性超过阈值整帧置零”不能直接继承；相关性改为证据信号，是否抑制与双讲检测一起评估。
- AEC 线性输出、残余回声抑制、NS 与 AGC 的位置及参数需要整体评测，不把孤立 AEC 核等同于完整语音前端。
- 真实播放 PCM 以输出格式进入 render 路径；按硬件时间戳与排队延迟对齐到采集时钟。不能把刚写入队列的采样当成已经发出的声音。
- 停止后保留有限物理尾迹；暂停/恢复、flush、设备切换分别更新参考，不播放的帧不能继续充当参考。
- 正式运行只保留必要短环形缓冲，不持久保存录音。

### 8.3 多路声音的边界

Agent 的输出可控，网易云/QQ 等其他 App 的声音通常没有本项目可用的数字播放参考。不通过秘密录屏或音频捕获权限取得它们的声音。

唤醒与对话可按系统音频焦点请求降低音乐音量；若目标 App 不配合或背景人声复杂，报告并评测实际表现。训练报数与跑步播报应通过明确的应用内焦点协调，不能顺带重写这些功能，也不能把所有外部音乐声都称为可被精确消除的回声。

## 9. 唤醒、连续对话、判停与打断

### 9.1 唤醒

待机只运行必要 KWS；不要求声纹资料。收到唤醒保留约 300–500 ms 的可调预卷，避免丢失紧跟的请求。

同一唤醒事件有唯一 ID，在处理完成前合并重复 KWS 命中；时间窗口仅用于去重，不用于判断“我要听歌”等意图。助手自己说到 BLACK 时，利用播放参考及声学证据避免再次唤醒。

模型先完成初始化再交付唤醒输入；初始化期间唤醒有短暂有界待办，失败明确显示未就绪。单喊名字只由业务 Agent 回答一次，不添加本地“我在”、第二个提示语或第二套音色。

### 9.2 草稿与判停

- ASR 的 partial/final 只更新一个 UtteranceDraft；识别器切段不创建业务消息。
- ASR 修订必须替换相应范围，不能把 partial 每次拼接导致重复文字。
- 判停证据包括音频活动、停顿变化、识别稳定性、语义完整性、上轮上下文；文本模型没有收到原始音频时必须明确这一点。
- 优先评估音频判停模型；不能直接把服务端 Python/Node 的 CPU 能力描述成手机端已可运行。[S7]
- 在没有合格音频判停模型时，采用本地活动证据加异步语义评估作为过渡，并明确其局限。每个草稿版本最多一个评估，新增有效发言使旧结果失效。
- 本地 300–800 ms 等窗口只作为候选与性能调参起点，不代表用户一定说完。不能仅因为静音达到上限，就把不完整指令交给写工具。
- wait 后继续保存草稿；检测状态变化或后续表达再评估，不死循环询问同一文本。长期无回应可退出会话或显示“还在听”，不反复抢话。
- 网络评估超时不默认执行；保留草稿、说明状态，恢复后也不重放已完成请求。

### 9.3 打断：软处理与真正取消分开

1. 有人声候选：继续采集、保存预卷、分析回声/双讲；不立即取消模型或销毁播放器。
2. 证据较强：允许短暂 duck，必要时 SoftHeld；输入和原回答均保留。不能像现有路径那样每个候选无期限暂停。
3. 判为噪声、回声或无关附和：撤销候选，恢复同一播放位置，不重新生成回答。
4. 判为有效交互/改口/要求停止：统一提交 UserInterrupted，取消指定 generation，flush 未播放音频，保留新发言并进入下一轮。
5. 新一轮使用“已经实际说出的范围 + 未说出的内容 + 已完成工具回执”，不假装用户听到了完整旧回答。

声学高置信的持续近端讲话可先停止/暂挂旧输出以免压住用户；是否发起新业务轮次仍由交互判断决定。低置信场景宁可短暂降低音量，也不凭一帧 VAD 直接销毁回答。

去掉声纹后，不承诺“只响应机主”。系统依靠当前会话及交互指向判断，旁人若明确向 BLACK 发请求也可能被接收；这正是本轮取消专属身份功能后的产品边界。

## 10. 语音合成、流式播放与字幕

### 10.1 合成引擎契约

SpeechOutput 接收文本片段，输出 `AudioFormat / AudioChunk / TextRange / End / Error`，每项带 generationId、segmentId。只有一个组件拥有扬声器和焦点；合成器不能私自调用系统 speak 导致无法取得 AEC 参考。

- 优先评测独立本地中文模型；发布前锁定版本、许可、文件摘要和性能结果。
- 不保留手机系统 TTS 提供者或回退分支；内置合成失败时保留文字、报告实际错误，不能偷偷更换为系统音色。
- 系统适配器区分初始化、入队、开始合成、音频产生、完成与失败；Android 提供 onBeginSynthesis/onAudioAvailable 等回调，但实际厂商支持仍须验证。[S3]
- 看门狗分别监测“初始化无响应”“首包无进展”“中途停滞”，根据真实进度续期，另设资源总预算；不再用统一 20 秒抹掉回答。
- 自定义 timeout 与 engineErrorCode 分字段；同一 segment 有限恢复，不自动重调 Agent、不重复执行工具。
- 已播放内容不重播；恢复粒度不够精确时说明“从本句重播”，不伪称逐字恢复。

### 10.2 增量文本与多轮工具输出

现有 personalChat 每个工具轮次调用 onRoundStart，会重置当前文字。不能把所有 onDelta 无条件直接送播放器，否则会读出中间草稿、成功宣告，随后又被改写。

改为明确的 ReplySegment 事件：每个模型轮次与可发声片段有独立 ID；区分口语进度说明、工具调用参数、最终回答。工具参数、协议、回执管理说明不进入 SpeechOutput。

生成器具备工具调用可能时，只发经过轮次协议确认可朗读的内容；不能用“已经生成了十几个字”猜测这是最终回复。若当前供应商只能在轮次结束确认是否有工具调用，该轮延迟到确认后输出，并记录额外延迟；升级到显式 speech 通道后才真正边生边读。不会为提速虚报工具成功。

已播放片段不可被后续 onRoundStart 从历史抹除。完整文字、发声片段和投递范围分开保存，但属于同一 Agent 对话。

### 10.3 播放

- 会话复用 MODE_STREAM AudioTrack，采用有界 PCM 环与回压；处理部分 write、underrun、pause、flush、路由变化及取消。[S5]
- 前瞻缓冲以时间计算而非整段文件数量；初始目标约 100–250 ms 起播缓冲、约 1–2 秒合成前瞻，实测调整。
- 长回答不得无限堆积 PCM，无法跟上合成时回压；播放超时不能丢掉已生成文字。
- 采样格式显式协商，不为迁就旧代码将所有音色固定降到 16 kHz；ASR 和输出可有不同采样率。

### 10.4 字幕与对话记录

- 模型文字生成即显示；实际播放范围在同一气泡标识，不能每块音频再创建一个回复气泡。
- 有音素/词级时间戳才做细粒度高亮；只有句级范围就做句级，不伪造逐字同步。
- 暂停与失败保留文字。打断记录“已说到哪”，不把未朗读部分当作已送达。
- 用户正在说话只更新草稿预览；正式提交后创建一次用户消息。
- 简洁要求留在表达提示层，不做硬字数裁剪，也不删掉困难问题和工具能力。

## 11. 与现有 Agent、配置和工具的整合

### 11.1 启动屏障

SessionReady 需要麦克风、必要模型、会话存档和连接配置分别达到已知状态。配置缺失可以明确显示“需要配置模型”，但不能靠发一条文字触发初始化。

loadConnection 的首次安装、modelVerified 改变与真正配置更改分流。只有用户明确更换当前模型/密钥等影响在途请求时，才按明确原因处理当前 generation；正常观察者通知不再等同 abort。

保留未就绪唤醒的短暂待办，不缓冲无限待执行的业务命令。JS headless 重建先加载存档与配置，再确认 pending turn 身份；不会重新执行已完成 mutation。

### 11.2 工具与事实

- runAgentTurn 与 personalChat 仍为统一业务入口，不另建“语音版饮食判断代码”。
- 工具意图、参数和是否需要使用工具继续交给模型；代码负责类型、权限、执行状态、持久化和幂等。
- TurnCoordinator 是交互信号处理，不是替模型回答问题，也不能按知识库范围拒绝输入。
- 音频取消不等于撤销已完成操作。继续使用稳定 requestId/operationKey 和真实回执，补测取消恰好发生在写入成功前后的竞态。
- 外部音乐操作结果不确定时先查状态，不因网络/音频重试自动重放；有意再次播放则由模型新指令发起。
- 旧对话里出现的 ownerVerified 等历史记录不是当前认证事实；新上下文不再沿用认证措辞。

### 11.3 协议与提示词清理

清除 responseStyle、turnAssessment、dialogue、通知及设置里的“已验证主人声音”描述。内部状态与用户文本分类型输入，不把协议段落当成可朗读回答；不能仅靠把整段文字加进 system 后祈祷模型不复述。

唤醒由模型回答一次；语音和文字均先说结论、简洁干练。禁止硬编码一长串固定业务答复替代模型理解。

## 12. 声纹退出、数据迁移与体积

实施时一并移除：登记 UI/API、认证门控、CAM++ 资源、VoiceBiometrics/VoiceIdentity/PacketGate/RegistrationGate 中只服务身份的路径、登记任务/进度、ownerVerified 字段及强制声纹构建检查。

KWS、普通 VAD 和 AEC 不能因为曾被声纹流程引用就误删；逐项确认新调用者。身份专用测试删除或移到历史，不保留“必须先登记”的断言阻碍新架构。

旧个人声纹文件和密钥不会被新链路读取或上传。迁移前明确通知用户并确认旧声纹的清理方式；如果暂时保留，只保留隔离数据与可删除入口，不保留整套运行认证模块。训练、饮食、音乐偏好、聊天和 API 配置不受影响。

资源清单重新生成，不只从界面隐藏。APK 逐项列出模型与 ABI 大小，优先提供 arm64 正式分发方案；不能为了缩包破坏现有支持机型，签名和更新渠道仍需校验。新 TTS 权重可能抵消删除 CAM++ 的空间，必须出实测差值，不先许诺包会更小。

可下载资源包需要版本签名/摘要、许可清单、原子替换与失败恢复；没有资源的设备明确“准备中”，不能下载未完成就显示可用。是否内置基础音色在 P0 根据体积与首次使用需求决定。

## 13. 系统生命周期、权限与隐私

- 由用户主动开启麦克风前台服务，显示可停止的通知；默认助手角色为可选入口，不能作为正常前台语音的必需条件。[S9]
- 已授权且服务持续存在时验证锁屏与切后台；不能承诺普通第三方 App 在强行停止后仍随时唤醒。
- 默认唤醒在本地；采用本地 ASR 时只把确认输入交给现有模型。若改成云音频，必须更新明确的音频上传说明，不能继续沿用“音频不上传”。
- 不默认保存原始音频。诊断默认只含阶段、耗时、队列/错误与匿名身份；导出录音需独立主动同意、可删除、有期限，不上传密钥或完整私人聊天。
- 唤醒不是身份认证。取消声纹后，任何能被识别为交互对象的人可能发起工具请求；不把唤醒误称为授权证明。现有工具权限及系统锁屏边界照常生效。
- 其他 App 抢麦、来电、蓝牙、音频焦点丢失、系统静音分别处理；不要全部合并为“识别失败”。

## 14. 用户界面：少量、清楚，不另造复杂控制台

现有 Agent 页保留对话和手机输入框，只补齐：语音会话开关/入口、静音、结束、简洁状态和可展开错误。

普通用户看到“正在听”“正在回答”“麦克风暂不可用”“语音播放失败，文字已保留”等可行动信息；不显示 DSP 分数、ownerVerified、内部控制 JSON。继续支持文字、附件和清空上下文，不因语音重构丢失。

设置只保留必要项：BLACK 唤醒、音色、输出设备相关选项（由系统能力决定）。删除主人登记与独立复杂阈值配置。训练页面的喇叭不是 Agent 会话入口，维持用户此前要求。

## 15. 错误、诊断与可复现实验

错误结构至少包含 `stage, category, provider, originalCode, internalCode, retryable, turnId, recoveryAction`；timeout 的 originalCode 为 null，不能制造 -4 系统返回。

阶段：permission、capture、front_end、recognition、turn_decision、model、tool、synthesis、playback、bridge。记录事件的单调时钟与先后因果，能区分“没采到”“采到没识别”“识别没提交”“提交没回复”“有回复没音频”。

开发诊断面板可导出最近一次会话事件摘要；默认不含音频和私密文本。保留缓冲上限、节流和自动清理，不把日志自身变成性能问题。

重构前先固化以下复现样例：首次启动不打字；外放长答；20 秒以上回答；慢速修正；助手说到 BLACK；蓝牙切换；配置首次加载/验证通知；工具成功时打断；合成第二段超时。

## 16. 测试矩阵与发布门槛

以下数字是拟定的工程验收目标，不是当前已达到的实测结果。先在 P0 固定设备档位、距离、音量、网络、语料及标注方式；正式结果附实际分母和失败例。

| 项目 | 验收方式/初始门槛 |
| --- | --- |
| 首轮可用 | 在权限、配置和资源完备的条件下清进程冷启动 20 次，不先输入文字；20 次均能完成首轮对话。另测依赖缺失的真实错误提示，报错不计为成功对话 |
| 自我触发 | 外放 30 分钟，含 BLACK、短句、长回答及多音量；指定测试集零自触发/零自我取消；不外推为所有环境零错误 |
| 长回答稳定 | 至少 20 段、每段 60 秒以上，除主动打断外均完整播放；包含 OPLS 原厂引擎故障注入与独立引擎 |
| 慢速表达 | 至少 100 条中文停顿/改口语料，预先标注结束点；过早提交目标 ≤2%，报告实际比例与样本 |
| 有效打断 | 至少 100 次近场插话；正确接受目标 ≥95%；话音起点至声音停止 P95 目标 ≤500 ms，明确测量不是从模型返回开始计时；另报候选确认、generation 取消和新请求提交耗时，不能用短暂静音冒充已完成打断 |
| 无效打断 | 至少 100 条噪声/回声/附和样本；错误永久取消目标 ≤2%；同时记录短暂 duck/SoftHeld 频率，不能掩盖听感卡顿 |
| 首声与延迟 | 分别报告 wake→ready、语义结束→首 token、首 token→首音、整体首声；正常网络简单问答端到端 P95 目标 ≤2.5 s，不把工具耗时混入纯问答指标 |
| 工具正确 | 至少 50 组音乐/饮食/训练查询及取消竞态；已成功写操作不因重连或播放失败重复执行 |
| 流与竞态 | 重复/乱序/迟到事件、JS 重载、native 重建、部分写入、取消后旧音频回调均有自动测试 |
| 生命周期 | ColorOS 16.0.10 实机，前台/锁屏/切后台各至少 30 分钟；权限撤回、来电、输出路由变化不崩溃 |
| 资源 | 无持续队列增长；30 分钟热稳定测试，记录 CPU、峰值内存、掉帧、耗电与温升；针对 P0 硬件预算定量通过 |
| UI/字幕 | 一次用户提交一个消息；语音与文字同会话；无协议泄漏、重复“我在”和假逐字同步 |

补充设备：至少一个 AOSP 环境、一个中端 ARM64 手机；模拟器负责自动化，不代替物理外放。耳机、蓝牙及嘈杂场景单列结果，不能用安静近场平均值覆盖。

对照豆包：相同设备、距离、音量、网络，使用同一批慢速、打断、回声样例；人工标注误抢话、有效打断、无效打断、首声和长对话完成率。未经运行对照只称“设计对照”，不能称 A/B 验收。

语义测试必须有真实模型的一小套有预算评测；全 mock 只能证明编排，不证明判断准确。涉及私人内容或额外费用先确认。

无需 USB 的验收方式：使用正式签名候选 APK，由用户在手机内完成固定短场景并查看结果；诊断页导出经过脱敏的阶段时间线。开发环境可自行做公开语料回放、模拟器和可用 ARM 环境验证，但这些不能替代真实手机扬声器—房间—麦克风闭环。没有真机结果时，对应项保持未验收，不发布“已全修复”的结论。

| P0：基线与选型 | 复现事件、候选前端/TTS/判停原型、体积/许可/性能清单、首版黄金语料 | 选出能在目标设备运行的基础组合；不能靠接口名宣布可用 |
| P1：会话地基 | 新 controller/事件协议/启动屏障；取消作用域；去除声纹必需项 | 冷启动无需文字；配置观察不取消；迟到结果不复活；一个会话所有者 |
| P2：音频闭环 | 采集隔离、前端选型、持续播放器、真实参考、焦点与路由恢复 | 无模型也能用测试音频证明长播/双讲/暂停/取消正确 |
| P3：正常对话 | 草稿/判停/软打断、文字及语音片段、现有 Agent 和工具贯通 | 同一套现场语料通过；不再依赖主人登记 |
| P4：真机优化 | 外放/蓝牙/锁屏/慢速/长答对照与故障恢复；逐项修正 | 达到上述基础门槛，明确原生语音能力仍有的差距 |
| P5：切换与清理 | 切至新链路、删除旧路径和无用模型/测试/配置，迁移说明、正式 APK 检查 | 新链路为唯一生产主流程，回归与签名验证通过，真实手机验收后发布 |
| 模型升级里程碑 | 当原生声学理解是达标所必需时，评测音频模型与工具接入 | 费用/隐私/部署经确认，满足能力契约及同条件验收，不靠宣传替代实测 |

原型可在开发分支独立测试；生产不能同时保留两套完整语音主循环。模块提供者接口不等于保留旧架构。若要回滚，用已签名上一正式版本及明确的数据兼容策略，不让旧逻辑在后台长期潜伏。

不以“固定几天全部完成”替代阶段门槛。每阶段汇报可运行产物、实测数据、剩余问题，不反复发布只有编译证据的修补版本。

## 19. 仍需验证的决策，不伪装为已解决

1. 手机型号/SoC 与本地 TTS 的实时率、内存和音色质量；现知系统为 ColorOS 16.0.10，不凭系统版本猜硬件。
2. 哪组音频前端最适合该手机；系统 AEC 与软件 APM 的实际处理路径需要实测。
3. 音频判停候选是否有许可合适、可移动端部署的模型；LiveKit 文档的 CPU 支持不自动满足这一点。
4. 如果本地方案不足，是否接受自托管算力或商业音频 API；未确认前不新增成本或音频上传。
5. 豆包运行时的具体协议及模型配置仍未知；这些未知不妨碍自主设计，但限制“完全同架构”的表述。
6. 去掉声纹后的旁人交互能力不等于身份安全；本轮不会偷偷恢复白名单来掩盖问题。

以上属于实施中的明确验证门，不是把整份方案留空。默认授权范围内可以先完成本地选型与基础链路；涉及新费用、隐私路径或数据删除才需要用户决定。
