# BLACK 本地播报截断修复

日期：2026-10-16。基线：v1.7.19（8ece42a）。本轮修改安卓原生播报链路，不替换 MeloTTS、不增加云端服务、不修改 Agent 模型、工具权限或业务决策，不发布安装包。

后续用户要求快速上传，按 v1.7.20 / Android versionCode 29 打包发布本轮源码；不追加整套功能回归，仅做必要的产物、签名和版本核验。下述声学失败仍如实保留在正式更新说明中，不能把发布视为该问题已修好。

## 问题证据

1. 现有分段器把单独换行等布局字符也送入合成器。固定版本 Melo 模型的桌面探针已确认：独立换行、空白及部分纯格式片段可能返回零个音频样本；正常文本在同一实例之后仍能合成。这不是“同步调用还没返回就去读结果”。
2. 合成线程会提前生成后续片段。原实现遇到后段异常后直接调用 `finish()`，进而停止正在播放的前段。
3. 新增安卓回归在第一段真实 AudioTrack 播放已开始之后，让第二段合成失败。修复前该测试失败：第一段应完成的原文进度为 10，实际为 0。这证明了代码可以导致“第一句话还没读完就停止”，不是对用户手机日志的推测。
4. 原 30 秒无进展计时混用了任务排队、合成与播放状态。此前“没有返回音频”和超时仍是不同错误，不能把两者混为一谈。

用户曾复制的一段具体回复，在此前桌面探针中三个原始分段都能生成音频。因此不将所有手机中断都归因于换行，也不声称已拿到该次手机故障的完整原始分段和日志。

## 实现

- `VoiceSpeechChunks` 返回朗读文本及原文 `start/end`。仅朗读副本处理换行和常见 Markdown 布局，模型原文、历史、工具输入和页面显示不变。纯布局、标点和表情片段不请求空音频；原文跨度仍连续覆盖，不截断 Unicode 代理对。
- 音频与终止事件采用同一个有界 FIFO 队列。后续合成失败先排入终止事件，让前面已生成的音频正常读完，再准确报错；不谎报全文播完，也不静默跳过失败的有效文本。
- 引擎返回空音频只重试当前尚未播放的片段一次。其他异常、持续空音频、全静音音频保留真实失败。重试不会重新调用 Agent，不重复执行饮食、音乐等工具，也不重播前文。
- 移除旧的统一主线程计时器。`VoiceOutputProgress` 分别标记排队、准备、实际合成、缓冲和结束；等待缺失音频时才检查相应阶段的 30 秒上限，已经正常消费的音频不会被合成阶段的计时器截断。播放器原有的实际消费停滞检查仍保留。
- 排队、准备、合成、焦点丢失有不同错误标识；失败信息携带片段编号及实际原因。不将准备失败错误地显示为“第 0 段”。
- 每轮音频焦点回调绑定本轮 generation。旧回调和取消后迟到的原生合成结果不能停止或完成新回答。
- 停止播放器时清除上一轮遗留的降音量状态；不修改系统媒体音量。
- `BLACK-VoiceOutput` 日志记录阶段、片段原文范围、排队与阶段耗时、重试次数、采样数和实际播放完成量，不新增录音或完整对话文本的持久化日志。

## 仍需区分的边界

- 这修复的是已复现的输出链路缺陷，不是“完整复刻豆包”验收。当前仍在模型最终回答后进入本地合成，没有新增模型文字增量到音频的流式协议，也没有更换音色模型或提高最终播放采样率。
- 合成器的同步原生推理不能安全地通过中断 Java 线程强杀。取消后会丢弃迟到结果；若原生调用本身一直不返回，后续请求会准确报告排队超时。本轮没有引入并发重建引擎或隐式系统 TTS 备用来掩盖该问题。
- Android 模拟器的本地模型、播放和模拟声学测试不能代替 Find X8 Pro / ColorOS 16.0.10 的外放双讲、蓝牙、锁屏与性能验收。正常音频焦点丢失、系统静音和真正的用户打断仍应停止输出。
- 正式工程的 ARM64-only 配置和模型资源未改变；源码修改需要新 APK 才会在手机生效，浏览器刷新或纯 JavaScript OTA 不能更新这些 Kotlin 代码。
