# Uncover 饮食板块：上线条件与用户可用性审核

审核日期：2026-09-28。审核对象：当前本地工作区 `D:/001号仓库/calisthenics-app`，不是 GitHub 上的旧版或已安装的 APK。

## 结论

**目前不具备“完整 AI 营养服务面向公众正式上线”的条件。**

本地饮食记录、营养计算、推荐菜单、历史参考目标和确认后执行的菜单工具已经形成可用闭环。它不是只有外观的演示页面，但也不能等同于已验证的企业级营养服务。

现阶段适合继续本地验收。健康成年人的有限内测需要先解决下面的数据问题，并准备可访问、受保护的营养服务。若产品定位为纯本地饮食日记，可不依赖 AI 或云同步，但仍要完成数据修复、备份恢复与安卓真机验收。

本次只审核饮食，不调整营养算法、记录结构、后台部署或发布状态；跑步页的 UI 与记录流程是另一项已实施任务。

## 审核方法与证据边界

- 阅读饮食页面、设置/记餐/相机/助手组件、菜单与历史算法、存储层及服务端实现。
- 在独立 Chrome 浏览器上下文中执行真实页面操作，使用虚构用户与测试数据，不接触用户当前标签页或记录。
- 识图与问答接口使用模拟响应；没有发送真实餐食、健康资料或付费模型请求。
- 只对本机 `http://127.0.0.1:8787/health` 做只读连通检查：**审核当时无法连接**。这不证明 API 密钥无效，也不证明不存在其他远端服务。
- 仓库中的 `eas.json` 未直接配置营养公网地址；EAS 远端环境变量、正式服务器和手机已安装包本次未查验，不能替它们出具上线通过结论。
- 这是专家任务走查与自动化验证，不是招募真实用户后的可用性研究；没有编造 SUS 分数、识别准确率、平均延迟或留存率。

## 能力是否真的具备

| 能力 | 当前情况 | 用户可用边界 |
| --- | --- | --- |
| 手动记餐、生活份量选择 | 已验证 | 不用联网；可选择碗/个/份等参考份量，也能填写实际克数 |
| 食物营养计算与修改/删除 | 已验证 | 按选定食品与份量核算；数据库通用值不等于用户实际餐食的检测值 |
| 收藏、最近餐食复用 | 已验证 | 生成独立的新记录，不倒改旧记录 |

| 减脂、增肌、维持、训练供能 | 有起始估算与用途说明 | 成人公式及产品默认规则；未完成营养专业审核，不能称为医疗处方 |

| 历史目标、完整记录周回顾 | 已验证 | 不补造历史目标，不把漏记算为没吃；比较只使用可比的完整日期 |
| 云同步、换机恢复 | 未实现 | 有 JSON 导出，但没有应用内导入恢复、账户同步或异地恢复闭环 |

DeepSeek 官方当前文档明确支持 `deepseek-flash` 的图片输入，因此问题不是“模型根本看不了照片”。**模型支持输入，并不能证明此账户、服务、餐食识别结果已通过验收。** 来源：[DeepSeek Vision 官方文档](https://api-docs.deepseek.com/guides/vision/)。

## 已做得好的部分

1. 已吃记录、推荐菜单与历史参考目标相互分离。换餐不自动计入摄入；助手草案必须预览确认，且提交时重新检查数据是否变化。
2. 95 项营养测试覆盖份量计算、旧记录快照、重复确认、修改/删除、健康筛查、过敏筛选、历史目标、记录完整度及菜单工具。
3. 服务端 79 项测试覆盖非法图片、超大请求、超时、断连取消、限流、上游失败、不合格模型结果和高风险问答拦截。
4. 照片先征得本次同意；未同意不上传。结果仍须确认才写入；失败不会新增一条虚构摄入。图片不放进饮食日志，拍摄/压缩临时文件有清理路径。
5. API 密钥保留在服务端，移动构建排除后台和密钥文件。照片结果明确标记估算，用户可删错项、修改份量、替换本地食物和补用油。
6. 不对未成年人、孕哺、相关疾病/药物、进食障碍风险及偏低体重继续自动量化配餐；低碳/生酮未审核时不强行开放。这与成人估算需要明确适用范围的原则一致。[NIDDK 成人体重规划工具适用范围](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner)。

这些属于已经验证的基础，不代表真实模型准确性、安卓端表现或安全认证通过。

## P0：当前阻断公开 AI 营养服务发布

### R01：没有经过验收的生产联网链路

依据：`src/nutrition/agentClient.ts:20`，`server/index.mjs:179`、`:268`，`eas.json`。

- 默认本地网页指向 `127.0.0.1:8787`。手机中的 loopback 指手机自身，不是开发电脑；原生端没有正式地址时直接提示未配置。
- 服务器只监听本机，并拒绝非本机 Host。这是合理的开发保护，但不能直接当公网服务部署。
- 本次实际 `/health` 无法连接；没有真实照片→公网 API→模型→确认→手机重启还原的全链路证据。

发布门槛：准备明确的 HTTPS 公网服务；在正式构建中验证地址、TLS、模型可用性、余额不足/断网/超时及弱网重试。不要为了让它联网而简单放开现有开发服务器。

### R02：生产鉴权、额度和运维闭环未实现

依据：`src/nutrition/agentClient.ts:44`，`server/index.mjs:125`、`:169`。

- 客户端没有用户/设备请求凭证；本地 Host/CORS 限制不是生产用户鉴权。
- 当前额度为每 IP 12 次/分钟、全局 30 次/分钟、全局滚动 24 小时 120 次，最大并发 2；全部只在进程内，重启丢失。
- 请求被拒绝时显示错误，不提供生产任务队列、分用户配额、费用预警、请求追踪或可观测性。
- 若连续识别每轮几乎没有耗时，理论上每分钟可接近 5 次；当前 120 次共享限额不能作为多人服务容量设计。这里是规则推算，不是已测吞吐量。

发布门槛：受保护的匿名设备会话或账户鉴权、持久化/分布式配额、费用上限、日志脱敏、可用性与错误告警、模型回退/关闭开关。客户端不得保存供应商共享密钥。[OWASP MASVS 安全控制范围](https://mas.owasp.org/MASVS/)、[MASVS 网络保护要求](https://mas.owasp.org/MASVS/controls/MASVS-NETWORK-1/)。

### R03：识图质量、营养内容与安卓端均缺生产验收

依据：`server/index.mjs:10`、`:217`，`server/validation.mjs:110`，`src/nutrition/vision.ts:47`，`app.json`。

- 当前照片营养由视觉模型直接估算，没有逐项食品数据库检索证明。服务器及客户端确实会拒绝明显不可能的宏量/热量组合，但格式与下限校验不能验证真实份量、用油、漏识别或菜谱正确性。
- 参考热量区间也是模型输出/本地按比例调整的区间，没有统计覆盖率校准；页面已明确它不是置信区间。
- 没有称重、已知配方和包装标签的独立餐食基准，也没有执业营养专业内容审核记录。
- 本次是 Chrome 页面测试，不是 Android CameraView、相册、权限永久拒绝、键盘、低内存、弱网、安装升级后的真机验收。

发布门槛：真实端到端调用和安卓测试；建立多种餐食/光照/容器/烹法的对照集；记录识别错误、热量/蛋白/脂肪偏差、拒识率和用户纠正成本。没有验证前，只能宣传“照片估算＋确认记餐”，不能宣传“拍照精确测量”。

### R04：健康资料与第三方处理缺正式隐私验收

依据：`src/components/nutrition/FoodCameraModal.tsx:269`，`src/components/nutrition/NutritionAgentModal.tsx:60`，`src/store/AppStore.tsx:259`。

- 已有简短说明与本次同意，但没有可打开的完整应用隐私政策、对应处理方政策、处理/保留周期、撤回途径和一致的同意版本管理。
- 助手会发送营养偏好（包含风险、过敏标记）、今日与周摘要、问题和近期对话；需要对这些实际数据字段进行正式隐私评审。
- 本机 JSON 使用 AsyncStorage，没有额外的应用层加密设计。系统本身可能提供沙盒和设备加密，本次没有否定这些保护；尚缺敏感数据威胁建模与备份策略验收。

发布门槛：确认处理方和部署地区、最小化字段、政策与撤回/删除闭环、数据保留方案、设备存储保护和导出提示。本报告不是法律合规认证，不声称当前实现违法。

## P1：本次复现的数据和可用性问题

### R05：营养档案不是一次一致性提交

依据：`src/components/nutrition/NutritionSetupModal.tsx:48`、`:50`。

复现步骤（隔离测试）：

1. 旧档案为健康成年用户，已完成筛查，可显示菜单。
2. 打开营养设置，体重从 75 改为 76，并勾选“有需要饮食管理的疾病”。
3. 只模拟营养日志保存失败，个人资料保存正常。
4. 页面提示“基础资料已保存，但营养偏好保存失败”；读回体重是 76，新的健康风险没有保存。
5. 关闭设置后，旧自动菜单仍可显示。

这是有明确错误提示的部分保存，不是静默成功，但仍会造成用户以为健康风险已影响后续建议的风险。

修复方向：身体数据与营养偏好采用可恢复的一致性提交；风险确认失败时自动配餐要安全暂停，不能只让用户记住“请勿离开”。建议进入下一发布门槛。

### R06：Web 多窗口后写覆盖先写

依据：`src/store/AppStore.tsx:252`、`:259`。队列只保护同一 Provider 实例。

复现：同一测试浏览器中，两个窗口都先加载旧日志；窗口 A 新增鸡蛋后，窗口 B 新增牛奶。最终本地持久化只剩 1 条，A 的记录不再存在。

这个问题已在两个独立页面实际操作中复现。它属于 Web 多实例，不应误报为“同一安卓界面快速点击必然丢数据”；后者的队列与测试已具备。

修复方向：存储版本与冲突检测、跨窗口通知/锁定或多写者安全存储。未修复时网页验收不要同时多窗口编辑。

### R07：“服务已连接”不足以代表识图可用

依据：`server/index.mjs:200`，`src/components/nutrition/FoodCameraModal.tsx:273`。

`configured` 只判断服务端是否存在非空密钥，不检查密钥有效性、余额、模型权限或上游健康。本次模拟 `/health` 为 true、识图返回 503：界面仍显示“营养服务已连接”，之后识图失败。

已有可读失败提示，失败没有新增摄入；需要把“后台可达/已配置”和“识图能力可用”分开，并让可用性检查有明确成本和缓存边界。

### R08：营养助手对实际数值问题帮助有限

依据：`server/knowledge.mjs:4`、`:84`、`:100`。

- 当前知识库是 5 条固定证据摘要＋关键词选择，没有向量检索、广泛食物知识或专业内容更新审查流程。
- 提示和校验禁止答案出现任何数字。因此“根据现有记录，我还差多少蛋白质”等常见问题不能直接得到数值回答。
- 使用纯函数探针，包含“还差 20 克蛋白质”的模拟回复会被拒绝；这不等于用户已经吃了这些量，也不涉及真实模型调用。

修复方向：已知摄入和剩余量用确定性本地工具生成可追溯回答；LLM 解释原因。增加证据版本、适用范围和可测评问题集，而不是让模型自行重算处方。

### R09：常见外食、品牌食品与偏好覆盖不足

依据：`src/nutrition/catalog.ts`，`src/nutrition/types.ts`。

- 当前只有 **51 种参考食物、20 道配方、102 个独立生活份量选项**。适合基础日记和受限菜单，不等同于覆盖国内早餐、外卖、火锅、复合菜、奶茶和品牌食品的商业数据库。
- 支持手动按包装创建食品，但没有条码/OCR；标签输入以克为基础，不支持直接将每 100 mL 当作每 100 g。
- 只有 8 类过敏筛选，其他过敏只有文字提醒，缺少“其他过敏→暂停自动菜谱”的结构化设置；不爱吃/不耐受/食材不可获得也缺明确偏好。
- 当前字段主要为能量、蛋白、碳水、脂肪与纤维，没有钠、糖、微量营养素或完整生酮专项审核，所以不能宣传“全方位营养检测”。

修复方向：先定义目标人群常吃的食物与配方覆盖清单，逐批核对来源、单位、生熟状态、过敏标记和许可；增加偏好与外食估算入口，不把缺失项目硬塞成精确数据库值。

### R10：备份导出没有恢复闭环；长期容量未验收

依据：`src/screens/ProfileScreen.tsx:65`、`:84`，`src/store/AppStore.tsx:295`。

有本机 JSON 导出和清除，但没有应用内导入恢复、云备份或换机流程。食品记录与日志保存在同一 JSON，新增/编辑需要重新序列化；当前验收没有覆盖长期高条数日志、存储空间满、应用被杀与旧版本迁移的安卓真实场景。

修复方向：先提供可校验的本地备份恢复；对三年记录规模做测量，再决定是否迁移 SQLite。云同步是产品选择，不是所有本地日记必须具备的功能，但需要如实标注范围。

## 用户可用性评估

| 用户任务 | 实际走查结果 | 主要摩擦 |
| --- | --- | --- |
| 第一次记录一餐 | 可完成；没配餐档案、没后台也能用本地食物记餐 | 食物覆盖窄，复杂外食仍需拆解或手动录标签 |
| 看今日已吃与参考量 | 可完成；真实摄入与推荐分离，未记餐显示空态 | 概念多：已记录、完整确认、推荐、历史参考需逐步引导 |
| 首次生成菜单 | 设置入口可用，风险筛查实际生效 | 320px 下表单内容高 1951px，滚动视口 706px，约 2.8 个视口；首次决策成本较高 |
| 照片识别与纠正 | 在模拟响应下可完成；不同照片重置旧说明，删项、半份、补油可保存 | 服务、授权、同意、拍照/选图、纠正、确认多步；还未测真实餐食的纠正成本 |
| 按照片默认记到合适餐次 | 18:30 测试仍默认选午餐 | 容易误记；应参考时间/所选建议餐次，但允许用户改选 |
| 询问饮食问题 | 模拟问答与草案确认闭环可完成 | 数字问题只能回到目标卡；关闭即清空对话，没有长期教练记忆 |
| 纠正、复用、删除记录 | 已验证 | 改名不会自动重算营养，需明确教会用户“换食品”而非仅改名 |
| 断网/接口失败后继续使用 | 本地记餐、菜谱规则继续可用；照片失败不新增摄入 | 识图不是离线能力；健康状态与实际可用性需要分开 |

P2 界面与引导问题：

- 营养设置底部仍写“未连接云端模型”，与其他位置的联网助手说明不一致，应明确“本次档案设置只在本机保存”。
- 相机餐次 radio 在 Web 实测只有选中颜色，`aria-checked` 都为空；需要补充可被辅助技术识别的选中状态。设置页已有显式 `aria-checked`，不是所有页面都缺。
- 档案有 10–11px 辅助文案，首次页信息较密集。按钮走查中预算选择高度是 44px，不能误报为触控尺寸全部不达标；仍需系统大字体和安卓 TalkBack 测试。
- “按已吃调整”要求完整确认前餐，逻辑正确但操作不直观。建议把当前缺少的确认直接做成入口，而不是只返回长解释。
- 已记录餐食仅在配方完全匹配时显示配方示意图；照片估算记录用相机占位，不冒充真实用户照片。只有 4 组示意资产，视觉丰富度距离模板仍有差距，但不能通过错图掩盖。
