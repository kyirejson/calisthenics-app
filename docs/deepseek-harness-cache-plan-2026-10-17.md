# DeepSeek Harness 缓存机制解构与 MAX 落地方案

日期：2026-10-17。本文保留最初的调研基线和设计；后续实现、与方案的差异及验证结果见 [实施记录](D:/001号仓库/calisthenics-app/docs/max-agent-cache-implementation-2026-10-17.md)。下文“当前代码”指调研时的代码，不代表实施后的现状。

## 结论

建议移植 DeepSeek 官方 Harness 的“不可变会话日志、稳定请求前缀、变更追加、可追溯压缩”思想，不把整个桌面 Harness 搬进手机 App。

MAX 目前并非完全没有缓存设计：单次任务的工具循环会追加历史，也已有真实 usage 和参数化手机流程。主要缺口是跨用户轮次会从 UI 记录重建模型历史，而且文字、语音会改变前面的提示与工具集合。把最新记忆放到历史后方只是局部改善，没有解决这一层。

本方案不通过关键词决定用户意图，不删主模型工具，不设置固定工具轮数，也不以历史成功答案冒充本次操作成功。模型仍决定做什么、选择什么工具和是否复用流程；代码负责忠实保存、提供资料、执行和记录真实结果。

调研阶段只新增本文档，未改业务代码、未读取密钥或私人会话、未调用收费模型、未运行测试、未打包或发布。后续用户批准的实施另行记录，不将其验证结果混入调研证据。

## 2. 先分清四种不同的“缓存”

| 层次 | 复用什么 | 主要收益 | 不能代表什么 |
| --- | --- | --- | --- |
| DeepSeek KV 前缀缓存 | 已计算的相同输入前缀 | 减少重复输入计算和对应计费 | 不是直接重放上次回答，不能证明手机任务已完成 |
| 本地内容存储 | 附件、知识、工具大结果的不可变版本 | 少传重复正文，保留完整读取能力 | 旧读屏不能冒充当前界面 |
| 手机流程复用 | 模型已核实的参数化操作路径 | 减少逐次读屏、点击的模型往返 | 路径执行完不等于用户目标成功 |
| 执行幂等账本 | 同一次请求的真实执行状态 | 重试/重连时避免重复发送、重复记账 | 不能跳过另一条真正的新请求 |

前两类主要改善输入成本；第三类直接改善“点得慢”；第四类保障正确性。必须分别统计，不能混成一个命中率。

## 3. 官方 Harness 的关键机制

### 3.1 KV 缓存由服务器自动管理，不是 Harness 自己实现了一个 KV 引擎

当前官方规则是匹配已经持久化的完整前缀单元。SWA 下，请求输入/输出边界、检测到的公共前缀及固定间隔都可形成单元。连续追加最有利于保留可复用前缀；只共享一小段开头，不代表下一次立刻命中该段。构建需要时间，命中是尽力而为，闲置缓存通常会在数小时至数天内清理，输出仍重新生成。[DeepSeek 当前缓存文档](https://api-docs.deepseek.com/guides/kv_cache/)

2024 年“64 token 一个块”的介绍是历史资料，不能当作现在唯一的规则，更不应据此给 MAX 填充凑块文字或制造付费预热请求。当前固定间隔的具体数值、内部放置与淘汰策略没有公开。

### 3.2 真实模型历史从日志派生，不从聊天气泡倒推

Session 记录有身份的用户、助手、工具结果及系统消息；消息内容冻结。deriveMessages 增量处理新增节点，已有节点不因 UI 展示而被重新编写。压缩是显式、有来源的替换，原事件仍保留。原始流片段、生命周期日志不会全部混进模型上下文。[固定提交 Session 源码](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/core/session/src/index.ts)

发布代码对应：dsh-session/lib/index.js 的 1441–1475、1530–1568 行。普通尾部增长只处理新增消息；发生替换才重建派生表面。这既防止客户端自身篡改前缀，也减少重复构造的工作。

### 3.3 提示词、工具和每次调用的配置有稳定次序与冻结边界

系统提示由有序 section 组装，运行时 context 与长期规则分离，工具按明确规则排序。绑定一次调用后，输入快照不能被另一处配置更新偷偷改变。相同渲染不重复产生新系统消息；能力不支持历史中系统更新时，明确按兼容规则重建，而不是假装前缀未变化。[System Prompt](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/core/system-prompt/README.md)

运行时事实仅在快照变化时提交；重试不重复加入用户输入。中断保留实际已交付内容，未回答的工具调用有明确的未启动或结果未知状态，不自动把不确定操作再执行一次。[Agent Loop](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/core/agent-loop/README.md)

### 3.4 协议适配器保留内容顺序和必要回放字段

已发布 DeepSeek 适配器使用 Messages 协议，按内容块顺序处理文本、thinking、tool_use、tool_result，并保留同模型所需的 thinking signature 等回放信息。原始工具参数保存在持久历史；发往接口时再作该协议要求的投影。不能因此把 MAX 的 Chat Completions 直接换地址就算迁移。[DeepSeek 适配器](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/llm/llm-deepseek/README.md)

发布适配器 lib/index.js 的 1460–1557 行体现回放元数据与助手内容的对应关系，1577–1718 行体现序列化，1808–1819 行接收缓存统计。

另外，当前 Chat 思考模式文档要求：携带 tools 的请求须回传历史各轮所需 reasoning_content，即使其中某轮没实际调用工具。是否需要这部分，必须结合实际模型、thinking 配置及协议判断；不能为了省 token 无条件删掉，也不能据此断言现有所有非思考请求都已出错。[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

### 3.5 支持时把系统/工具更新放到历史后方，但不是通用 API 保证

发布包中，SystemPromptProjection 会在支持 in-history 的连续请求系列里追加变化，保留先前历史。工具声明还会依据已保存的基线和增量构造；addition-only 路由可以保留既有声明的布局，新声明以延迟加载方式加入，再在历史中激活。

可复核代码：dsh-agent-loop/lib/index.js 的 231–295、1041–1066、1201–1276 行；dsh-llm/lib/index.js 的 759–835 行；适配器 2187–2202 行会按内容发送相关 beta 标记。

这里存在兼容性边界：Harness 源码声明并使用这些能力，而通用 Anthropic 兼容文档并未完整覆盖它们，还把大部分 anthropic-beta 和 cache_control 列为忽略。因此，“Harness 能这样发”不等于 MAX 当前 Chat 接口或任意网关也能这样发。[公开兼容表](https://api-docs.deepseek.com/guides/anthropic_api/)

本方案第一阶段不依赖这些扩展。日后启用前，要按具体 endpoint、模型和协议确认能力；不靠模型名称猜测、不在失败后偷偷改成另一套请求协议。

### 3.6 文件按稳定引用读取；图片仍有前缀变化风险

Harness 将 FileBlock 投影为确定的文件句柄文字，模型按需读取保存的完整副本，而不是每次自动展开文件全文。模型输入与日志之间保留可重建关系。[LLM 服务](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/llm/llm/README.md)

适配器对图片使用确定的请求版本并复用 Files 上传，但文件引用刷新、路径变化或退回 base64 仍可能改变前缀。所以“图片字节相同”不等于“整个请求始终命中”。MAX 应借鉴内容版本与稳定句柄，而不是把截图永久缓存成当前画面。

### 3.7 压缩是有代价的换挡，不是免费保留命中

官方工具结果裁剪是在上下文压力触发后处理，保留头尾和原始日志，不调用模型做这一步。替换早期结果会损失从改动处开始的前缀复用。其裁剪本身不理解中间内容的重要性。[Tool Result Pruner](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/compaction/compaction-tool-result-pruner/README.md)

不照搬这种头尾截断去处理手机可操作节点。MAX 应保留完整原文读取出口，针对长期会话使用明确检查点；承认新检查点首次调用可能变冷。

### 3.8 真实缓存命中与估算分开

Harness 接收供应商 usage，另外有从日志回放的 token/context 估算。估算不产生新的模型请求，也不是账单；其固定字符启发式对中文和 JSON 可能低估，不适合拿来宣传精确节省。[Token Meter](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/llm/token-meter/README.md)

### 3.9 dsh_session_log 不是隐藏缓存按钮

官方会增量上传 session log，以确认水位继续发送后缀，HTTP 接受后才记录水位。它是 model-input 字段之外的元数据，官方文档明确其 KV Cache effect 为无。它增加 HTTP 字节，不把整个事件日志变成模型输入。[Session Log Upload](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/packages/session/session-log-deepseek/README.md)

MAX 不为提高命中照抄这个上传功能，更不把用户手机操作日志额外上传。不能从客户端扩展字段推断服务器有可供 MAX 使用的私有缓存控制协议。

## 5. 针对 MAX 的具体架构

### 5.1 一个 Prompt Journal，替换 UI 反推历史

新增手机端轻量模型会话日志，作为模型历史唯一真源。UI 气泡、工具进度、语音文本由它投影；不再维持两套能互相覆盖的历史。

保存的关键事件：

- 会话和前缀版本开始：固定系统规则、工具定义、模型与协议配置摘要。
- 本轮上下文：时间/时区、输入模式、真实唤醒状态及发生变化的记忆版本。
- 用户正式消息：ASR 已决定提交的整轮文字或文字输入，包含附件版本引用。
- 模型消息：完整工具批次、调用顺序、原始参数字符串、正文及协议必需的回放字段。
- 工具结果：绑定 callId 的不可变结果文本及执行身份。
- 重要投递事件：最终播完、用户打断、播放失败；不把每个播放进度回调都塞进模型历史。
- 显式检查点：原因、替代范围及原始历史的读取入口。

“不可变”指已提交内容不被 UI 回调原地修改，不是禁止模型纠正先前决定。纠正、撤销、记忆更新都作为新的事实出现。

持久化建议：Android 使用与当前 Expo SDK 匹配的 expo-sqlite，需增加依赖和重新构建，这是拟议变更，本轮没有安装。Web 通过 IndexedDB 事务适配同一 Journal 契约；两者只是平台存储后端，不是两套会话或业务规则。IndexedDB 本身提供事务型本地存储。[IndexedDB 文档](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

不默认在 Web 搬用 SQLite：Expo 的 Web SQLite 需要 WASM 和允许 SharedArrayBuffer 的隔离响应头，不能为了日志贸然改变可能影响现有地图/外链的全站环境。[Expo SQLite Web 要求](https://docs.expo.dev/versions/latest/sdk/sqlite/#web-setup)

新日志替代现有会话单键全量重写，不另外保留一个竞争的聊天数据库。写入队列和事务由一个模块拥有，不能把多个 AsyncStorage 写当成数据库事务。大附件在 Android 复用已有文件系统，Web 使用平台可持久的内容存储；数据库保存身份、版本、摘要与引用。正文先保存再提交引用，崩溃留下的孤立正文可清理，不能先发布指向尚未保存正文的引用。

原生手机/音乐的执行账本继续拥有真实副作用事实，不迁入或重写它们。日志引用其回执，避免让会话数据库承诺跨进程、跨原生工具的虚假原子性。

### 5.2 固定前缀版本，但允许模型和用户改变能力

一个 prefixEpoch 固定 provider/endpoint、modelId、thinking 配置、协议版本、系统规则版本、工具定义与次序。固定规则只放长期身份、表达偏好和工具使用协议，不放当前分钟、实时权限状态、联系人或动态个人记忆。

主会话优先使用统一规则和全部业务工具，文字/语音模式以本轮上下文告诉模型。语音控制工具在没有活动语音会话时返回真实不可用状态，而不是通过删除工具改变声明，也不影响其他工具。

工具名和 schema 属性使用一次确定的规范化顺序，规范化结果按版本保存。不能每轮根据最近用过哪个工具、当前 App 或关键词动态重排。

更换模型、协议或 schema 时允许建立新版本，并保留明确的历史衔接与完整归档入口。前缀冻结不是阻止更新；是使成本变化能被解释。未来若验证支持 Harness 那样的历史中更新，可在适配器中采用，不影响这套日志结构。

### 5.3 个人记忆和上下文只追加必要变更

初次建立会话可提交当前完整记忆快照，后续按 revision/hash 判断是否变化。没变不重复放整份 MEMORY.md；变了追加有基准版本的完整新快照，或可准确还原的变更。read_memory 仍能读取完整最新内容，由模型决定是否需要。

时间和模式在新用户轮次记录一次；同轮多次工具续请求复用当时的已提交事实，不每点击一次就生成一个新的时间字符串。任务跨日或需要精确当前时间时允许追加新时间事实。

重连后读取原生账本，只把新发现或尚未提交的结果追加回来，不把所有历史回执重新排到末尾。权限状态发生变化时如实更新，绝不为保持命中沿用失效授权。

### 5.4 传输层保存真实消息，UI 层继续实时输出

模型输出一边流向 UI/TTS，一边组装成该协议的真实消息。流结束时提交一次完整模型消息；用户打断时提交确实收到的有效部分及中断事件。不能把“只播出第一句”误存为“模型只生成了第一句”。

执行参数可以解析成对象，但解析副本只给执行器，不能回头覆盖原始参数字符串。工具结果在首次写入时序列化并保存，不在下一轮以另一种字段次序重新输出。

finish_phone_task 的摘要、静默继续听及回待机也保留原始工具调用和结果；UI 从明确的终结字段投影显示/播报，不另造一条模型没有生成的“总结”。网络、存储和 TTS 的 UI 错误属于系统事件，不伪装成模型曾说过的话。

包含工具调用的助手消息与待执行身份须先落盘，再交给原生工具。若进程退出后发现调用已开始但结果未知，先核对真实原生回执/目标状态，不能把它标成失败后自动重复发送。

批次中被取消且尚未启动的调用与已经启动但结果未知的调用分别闭合为真实状态，保留各自 callId，避免下一轮出现孤立工具调用。已完成结果从账本恢复，不能因补齐协议而重新执行。

协议适配器只做格式与能力映射，不夹带另一套提示词、业务意图路由或无依据的成功兜底。

### 5.5 语音判停有自己的稳定请求前缀，不污染业务历史

保留“语义判停”和“正式业务 Agent”的职责区分。两者仍可使用同一模型供应商；判停是辅助时序请求，不接管业务，不给主模型阉割工具。

同一段用户话语的多次判停使用冻结的已提交对话快照，把累计 ASR 候选放到末尾。wait/ignore 和临时识别修订不写成正式用户消息。只有决定提交时，把完整这一轮交给主日志一次。

必要的新执行状态以尾部事实提供，不能为缓存隐瞒正在发生的状态变化。对判停与主 Agent 分别统计命中，不把辅助请求的命中归给主业务工具。

### 5.6 大内容变成稳定资料，不让模型失去访问能力

新增统一 AgentArtifact 引用：artifactId、revision、内容摘要、类型、来源、字节数和完整读取能力。附件正文保存一次，引用不使用每轮变化的临时路径。知识库按真实路径与内容版本引用，不修改知识内容。

提供模型工具 read_agent_artifact，可按范围/游标读取，也可读取完整内容；没有隐藏的“只允许前几段”。传输块大小只是分页方式，不是限制能读多少。需要全文的任务仍会产生相应 token，不能声称引用让所有输入都免费。

工具结果首先保留 ok/code/uncertain/replayed、操作身份、结果证据和下一步所需字段。大段参考资料才分离为内容引用。活动读屏必须保留有效 snapshotId、window/display、节点与可操作目标；若改成分页，模型必须能读取任意页及完整树。

新鲜度与缓存解耦：旧画面可供回顾，但再次操作前仍检查快照有效性。应用变更、系统返回真实错误时，不能为了复用而继续点击旧坐标。

### 5.7 流程缓存继续作为模型可选择的“快捷手脚”

复用当前 [workflowRuntime](D:/001号仓库/calisthenics-app/src/device/workflowRuntime.ts:6) 和 [workflowTools](D:/001号仓库/calisthenics-app/src/device/workflowTools.mjs:3)，不再叠加第二个关键词路由器。

- 模型可读取已验证流程摘要/完整步骤，自行判断与本次请求是否匹配，并填入这次联系人、消息、歌单或地点。
- 模型选中流程后，一次工具调用让原生连续执行确定步骤，减少逐个点击的模型往返。
- App 版本、页面前提、目标唯一性和回执照常核对；缓存不合适就返回具体状态，由模型继续用原有手机工具探索。
- 不同请求不能因文本相似共用一次发送结果。相同请求重试沿用真实 operationKey，防重复效果仍由原生账本负责。
- 播歌后台模式保留原有音乐控制链路，不为了复用普通屏幕流程而占用前台。
- “流程命中”“步骤执行完”“用户目标核实成功”分别计数。

这是让执行变快的第二条主线，不把它包装成 DeepSeek KV 命中。

### 5.8 长会话显式换挡，不无限膨胀也不偷删历史

采用实际输入 usage 和模型容量判断上下文压力，不固定“只留最近 N 条”。接近容量时保存可回读归档，生成明确检查点，记录正在做的任务、已执行/未知操作、重要用户事实和资料引用。

压缩后承认前缀改变、统计冷启动。未完成的工具链、操作幂等身份和失败根因不能被摘要成“已完成”。原始记录可由模型继续读取；用户清空上下文时同步删除本地相关归档和资料引用，而不删除饮食/跑步等独立业务数据。

客户端没有清理供应商 KV 的公开控制能力，不能把“本地已清空”说成“远端缓存已立即抹除”。

## 7. 用什么判断真的优化了

### 7.1 增加诊断元数据，但不收集敏感正文

每个模型请求记录 taskId、requestId、callId、lane、modelId、provider/endpoint 标识、protocolVersion、prefixEpoch、systemDigest、toolsDigest、journalThroughSeq、前缀首个变化位置及 rewriteReason。

这些诊断信息默认留在本机，不为统计额外上传联系人、消息、正文、录音、屏幕或密钥。稳定身份使用本地生成的匿名 user_id；不能每任务换一个 user_id，也不能把手机号当标识。官方文档明确 user_id 可隔离 KV 缓存，Chat 与 Messages 的传法不同。[Rate Limit & Isolation](https://api-docs.deepseek.com/quick_start/rate_limit/)

Harness 自带的 x-deepseek-harness-user-id 是其自身请求标记，不冒充官方 Harness 来获取所谓特殊缓存待遇。

### 7.2 同时看六类指标

1. 供应商真实 token 加权命中率：总 hit /（总 hit + 总 miss），不平均各请求百分比。
2. 每任务未缓存输入 token、输出 token、请求总数和已知费用；缺失 usage 的取消/失败请求标未知。
3. 首 token、首可见文本、首工具调用、整任务耗时分别统计，不能混为一个“速度”。
4. 客户端历史结构是否只追加：相同前缀版本内首个差异在哪里、为何变化。
5. 流程复用是否实际减少模型往返，失败后是否正确由模型接管。
6. 目标正确性和副作用：发对人、无重复消息、没漏记录；不能用高命中掩盖错误。

本地 JSON 字节/消息结构的公共前缀只是排障代理，不等同于 DeepSeek 内部 token 前缀，也不能据此声称获得了多少命中 token。

Chat 的 prompt_tokens 已包含缓存命中与未命中部分；缓存计数及 cached_tokens 别名不能重复相加。保留现有先读 usage 再读 choices 的处理，兼容结束块和 usage-only 尾块。缺少计数不是 0% 命中。[Chat API](https://api-docs.deepseek.com/api/create-chat-completion/)

若以后增加 Messages，单独按该协议的 input/cache-read/cache-write 字段归一化，不套用 Chat 的计数分母。未知字段不猜测。费用使用当时实际价格配置，不在代码中以旧价宣传固定节省比例。

### 7.3 消耗重点：先给结构性优先级，不编造实测排行

| 优先检查 | 为什么可能昂贵 | 本方案对应措施 |
| --- | --- | --- |
| 多步手机读屏/OCR/导航/微信任务 | 每轮反复携带增长的历史与画面，同时有多次模型等待 | 连续操作工具、已验证流程、不可变工具历史、内容引用 |
| 长附件/完整知识/多次读取记忆 | 大正文进入历史后被之后每个请求再次输入 | 版本化引用、完整读取工具、记忆只提交变化 |
| 同一句话的多次语义判停 | 单次可能较小，但触发频繁；会叠加整段对话文字 | 独立稳定前缀、冻结已提交快照、候选放尾部 |
| 长会话和频繁文字/语音切换 | 前缀改写与累计历史同时影响 | 共用日志/固定业务工具、显式检查点 |
| 单次短文字问答 | 通常往返少，但完整工具 schema 仍有输入开销 | 稳定 schema，保留能力，不为省钱删工具 |

这是优化调查顺序，不是已经测出的 token 排名；语义判停高频时可能排到第一。真正排名应由现有 read_agent_usage 加上述归因后，在完整保留窗口内给出。

## 8. 实施顺序与后续验收设计

| 阶段 | 交付 | 完成判据 |
| --- | --- | --- |
| 1. 建立基线与日志真源 | 追加日志、协议消息完整保存、旧数据一次迁移、前缀诊断 | 从同一日志重放得到同一合法请求；不依赖气泡重建 |
| 2. 稳定主前缀 | 固定规则/schema、记忆和运行时变更追加、文字语音共用 | 正常下一轮不改变已提交的模型消息；时间/模式变化在新尾部 |
| 3. 压低重复正文与轮数 | 资料引用、流程接入同一证据与计数链、判停独立前缀 | 模型仍能读取全部内容，流程不可用仍能探索；任务往返可比较 |
| 4. 长会话与兼容扩展 | 检查点、恢复、按能力选择历史中更新 | 前缀变化有原因，旧工具状态不丢失；扩展失败不暗中降级 |

后续实施的离线协议回放至少覆盖：

- 连续两次用户输入；一次返回多工具及带空格的原始参数；工具中间有模型正文。
- 时间变化、记忆变化、文字转语音；默认规则/schema 未变化。
- TTS 播放失败、用户打断、待机后重唤醒；已执行操作不重做。
- 取消发生在工具开始前、工具执行中和结果提交后；未知状态正确恢复。
- 重启恢复、旧存档迁移中断、迟到回执、并发语音/文字入口。
- 附件全文读取、内容修改生成新版本、旧屏幕引用失效。
- 显式清空、模型切换、工具 schema 升级和上下文检查点。
- usage 出现在完成块、独立尾块、取消时缺失、同一累计计数重复出现。

真实 API 阶段才比较相同模型/协议/工具与相同任务的冷启动、后续追加、重启、更新/压缩后数据；只使用必要的真实任务，不循环空请求刷命中。先做无副作用回放，手机任务再核对具体目标。评价看任务成本、速度与正确性，不要求每个合法请求都命中。

上述均为将来的验收设计，本轮没有执行这些测试，也没有操作用户手机。

## 9. 预期结果与不承诺的事情

预期可交付：

- 结束一轮对话后，下一轮仍忠实复用此前模型历史，减少客户端制造的无谓前缀变化。
- 常用任务由模型自行选择已验证路径，减少逐次点击的模型往返。
- 模型继续有全部业务工具和全文资料访问能力；代码只提供稳定、可追溯的手脚。
- 能解释“哪次为什么失去前缀复用”，并按整次任务显示真实 token 与耗时。

不能承诺固定 99% 命中、固定节省比例、固定毫秒延迟，不能承诺仅靠缓存解决系统权限、微信空树、导航加载或所有外放声音识别问题。缓存也不能让没有官方接口的手机操作忽略系统边界。

实施重点是替换 MAX 的模型历史和请求组装层，保留已工作的业务与原生模块。不是再给现有历史重建逻辑外面套一层“缓存补丁”。
