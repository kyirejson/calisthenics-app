# 食物营养知识库调研报告

> 调研日期：2026-09-27 · 三个并行子代理完成（数据源 / 竞品机制 / 本地架构），关键数字均标注来源。
> 对标差距：薄荷健康 160 万+ 食物库；本地目前 51 条食材（基础 23 + 熟食调味 28）+ 20 个食谱，拍照营养靠大模型估算且无法逐项纠错。

## 一、结论速览（TL;DR）

1. **不存在可合法直接商用的"中国版薄荷库"**。中文侧最佳可用数据集是 GitHub [Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data)：《中国食物成分表》第 6 版转录，**1677 条**（能量/三大宏量 + GI 表 + 1260 条中英对照），活跃维护，但**无许可证**（转录自版权图书），只可作内部质量基准，商用分发前需获授权或重制。
2. **家常菜没有现成数据集**，业界（含薄荷官方披露）的通行做法就是"**配方合成**"：食材配比 × 成分表计算，GB 28050 认可该计算法。这是质量护城河，也是必须人工审核的部分。
3. **竞品共同原则（Cronometer 表述最清晰）：AI 只负责"报菜名 + 估份量"，营养数值一律来自可信数据库。** Uncover 现有拍照流程是"整餐估算直加"，应改造为"逐项识别 → 匹配本地库 → 用户逐项纠错 → 沉淀为自建食物"。
4. **最近/常吃/收藏置顶、"复制昨天的一餐"、组合餐、逐项纠错、自然语言加餐**——全部可以纯本地实现，不需要云大库。
5. **存储选型：JSON 打包进 bundle，不上 SQLite**（Web 支持是 alpha，1 万条线性扫描 1–3ms，收益不成比例）。拼音搜索用 pinyin-pro 在**构建期**生成索引，运行时零依赖。
6. **journal 保持 version:1**，新字段全部 optional 挂载——现有 `normalizeNutritionJournal` 对非 1 版本直接返回空日志（engine.ts:447），升版本会静默清空老用户数据。
7. **总工作量约 21–31 人日**，分三个里程碑。

## 二、数据源对比（子代理实测）

| 来源 | 规模 | 中国覆盖 | 许可证 | 结论 |
|---|---|---|---|---|
| 《中国食物成分表》第 6 版 | ~1700+（第 1 册） | 权威 | 版权图书，无开放数据 | 薄荷同款来源；需授权洽谈 |
| [Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data) | **1677 条** + GI + 中英对照 | 中国食材全覆盖 | **无许可证（商用风险）** | 内部基准 / 合规处理后使用；技术接入 2–3 人日 |
| USDA FoodData Central | SR Legacy 7,793 / Branded 43 万+ | 亚洲食材有限、无中文名 | **公有领域** | 补充品类 + 沿用现有 USDA 管线；3–5 人日 |
| Open Food Facts | 全库 400 万+ | **中国仅 1,684 条（实测）** | ODbL（需署名、同许可共享） | 离线条码小包可选；非主数据源 |
| FatSecret Premier | 230 万+ / 62 国（含 CN 中文） | 未验证 | 免费层仅美国数据；CN 需商业采购 | 中期条码规模化唯一合规渠道，价格未公开 |
| Barcode Lookup | 18 亿+ 条码 | 未找到公开数据 | $99–949/月 | 中国覆盖验证前不考虑 |
| ChinaFood-100 等学术集 | 图像 10 万级 | 中国菜肴图像 | 仅限研究 | 只作参考，不引入 |
| 薄荷数据爬虫仓库 | 近千条 | — | 违反 ToS | **禁止** |

**冷启动组合（0 → 2,000 条）**：成分表 1677 条（合规处理 + 与现有 51 条同义合并）→ 自建 150–300 道家常菜配方合成 → OFF 中国条码 1,684 条离线包 → USDA 补缺 50–200 条。中期（→1 万）：配方合成管线工具化扩到 2,000–3,000 道菜 + FatSecret Premier CN 接洽 + 用户扫码众包（参考 OFF 模式）。

**合规红线**：成分表数据不得原样进商用包；OFF 必须署名且改编库以 ODbL 释放；配方计算值/估算值前端明示"计算值/估算值"。

## 四、现状代码盘点（架构代理读码结论）

- 数据结构：`Nutrients`（types.ts:7）、`Food`（types.ts:19-30，**单个** serving、无分类/条码/份量数组）、`Recipe`（types.ts:32-41）、`IntakeEntry`（types.ts:69-84，含 customFoods 快照与 foodDataVersion）。
- 实际食物库：catalog.ts:33-87 共 **51 条**（基础 23 + 熟食调味 28，全部 USDA）；食谱 20 条（catalog.ts:96-197）；份量表硬编码在 servings.ts。
- 三条录入流：A 搜索→选择（IntakeEditor，搜索是 includes，无拼音/置顶）；B 拍照→DeepSeek 估算→PhotoFoodEditor 逐项纠错（**服务端 prompt 明确不查库**，server/index.mjs:10-15）；C 计划餐→确认。
- 关键守卫：journal version≠1 直接清空（engine.ts:447）；历史记录不重算（engine.ts:432）；自定义食物强制 `custom-` 前缀（engine.ts:356-378）；照片替换只查 catalog 不含自定义食品（vision.ts:137-139，**缺口**）。

## 五、架构方案

### 5.1 数据模型（全部 optional 新增，journal 保持 version:1）

```ts
Food 新增：category?: FoodCategory; servings?: ServingUnit[]; barcode?: string;
          sodium?: number; confidence?: 'measured'|'synthesized'|'user';
          search?: { full: string; initials: string };   // 构建期拼音索引
          source.kind 扩展：'user_label'|'user_photo_seed'|'usda'|'cfc6'|'off'|'synth'
Recipe 新增：perServing?: Nutrients（配方合成缓存）
Journal 新增：favoriteFoodIds?: string[]; recentFoods?: Record<id,{at,count}>
```
平滑性：`normalizeCustomFood` 只补默认值不改判定；摄入条目仍只存 `{foodId, grams}`（份量单位只存在于编辑草稿态）；51 个旧 id 一字不改。

### 5.2 存储与分发

- 内置库 JSON 进 bundle：`foods-core.json`（高频 1500–2000 条，静态 import）+ `foods-ext.json`（至 1 万条，动态 import）；source 字段枚举码压缩后 1 万条约 2.2MB raw / 0.8MB gzip。
- 用户自建食物继续走 `journal.customFoods`（≤200），统一容纳标签录入/拍照沉淀/代理沉淀三类来源。
- 升级 = 随版本发全量 JSON + `FOOD_DATA_VERSION` 版本串；历史条目永不重算。
- **不上 SQLite**（expo-sqlite Web 支持.alpha，见 expo#32918）；重估阈值：>3 万条或需 FTS5。

### 5.3 搜索（src/nutrition/search.ts，纯函数）

评分：前缀 100 > 包含 80 > 拼音全拼前缀 60 > 首字母 55 > 拼音包含 40；boost：收藏 +30、最近使用对数封顶 +20。pinyin-pro 仅 devDependency，构建期写死索引。接入点：IntakeEditor.tsx:44-45、PhotoFoodEditor.tsx:33-35（后者顺带修复"替换不含自定义食品"缺口）。

### 5.4 拍照闭环（对齐 Cronometer 原则）

```
拍照 → DeepSeek（prompt 升级：每项输出 名称+检索关键词+估计克数+家常份量+兜底营养）
 → 客户端 matcher.ts 在合并库上跑 search 评分
   ├─ top1 达阈值 → 绑定 foodId，营养值 = per100g × grams 实算（复用 vision.ts:48-49 可复算校验）
   └─ 不足 → 保留估算 + top3 候选 chips
 → PhotoFoodEditor 逐项纠错（候选 chips 一键换绑 / 保存为新食物）
 → 入账：绑定项走 portions，未绑定项保留估算语义
```

### 5.5 自然语言记账（LLM 只能引用知识库）

新端点 `/v1/nutrition/log-meal`：输入 = 用户话语 + 候选清单（~200 条，仅 id/name/servings）；输出只允许 `{op, slot, foodQuery, grams, servingLabel}`，**出现任何营养数值字段即整体拒绝**；客户端 matcher 解析 foodQuery→库内 id，解析失败进 unresolved（换选或新建入库），入账前强制逐项人工确认。

### 5.6 落地路线

| 里程碑 | 内容 | 工作量 | 关键风险 |
|---|---|---|---|
| M1 基建 | build-food-data.cjs 三源管道 + 数据模型扩展 + 搜索 + 置顶/收藏/最近 | 10–14 人日 | 成分表无许可证（内部基准）；catalog 改装载时 id 漂移（用旧 id 快照测试锁死） |
| M2 拍照闭环 | matcher + prompt 升级 + 候选 chips + 沉淀自建食物 | 6–9 人日 | server prompt 与校验必须同 PR 原子改；绑定阈值过松（阈值 + top3 人工确认双保险） |
| M3 自然语言 | log-meal 端点 + 确认列表 UI + 条码本地匹配（可选） | 5–8 人日 | LLM 输出漂移（json_object + 硬校验 + 整体拒绝）；误记账（unresolved 永不静默入库） |
