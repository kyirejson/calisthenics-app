# Uncover 饮食审核第三阶段：训练与营养闭环

2026-09-28，本地开发。此处的“第三阶段”指饮食审核后的第三批目标，接续 [饮食易用性记录](./nutrition-usability-phase3.md)，不是重新发布一个 APK。未上传代码、未部署服务、未调用付费模型。

## 用户能做什么

在“今日 → 饮食”中：

1. 查看真实训练日程、预计耗时和已经打钩的有效训练组数，选择早间、午间或晚间训练。
2. 记录摄入后，逐餐确认“这一餐已记完”。未吃某餐也可以明确确认；没有记录且没有确认不视为零摄入。
3. 使用“按已吃调整”或换餐工具，先看原餐与建议餐、营养差异、份量和做法，再确认应用。仅修改推荐菜单，不自动登记为已吃。
4. 查看每日目标的变更历史与七天复盘。历史日期按当日保存的目标比较，不拿今天的目标套用过去的记录。
5. 与营养助手连续问答。助手只能提出受限的菜单操作意图，菜谱和营养由本地规则核算，仍需用户确认。

换餐弹窗的确认按钮固定在底部；较长的食材、说明和做法可以在上方滚动。保存期间防止重复提交和关闭。

## 训练联动

`src/nutrition/training.ts` 读取当前课程、当天新增动作和训练记录，使用现有训练耗时估算，包括热身、训练、休息与整理。

- 力量训练只有已打钩且有效的组才计入实际训练；只打开界面不算完成。
- 跑步只有有效正时长才计入。兼容现有训练记录中的日期表示，不更改训练计划。
- 恢复日、计划课程和实际额外训练分别显示；训练时间不是自动增加可吃热量的依据。

训练时段只改变推荐餐的能量与碳水分配、菜谱及提示，不另算运动消耗，不抬高全日目标，不追逐所谓短暂“合成窗口”。全天摄入与个体耐受优先，这一定性原则参考 [ISSN 营养时机声明](https://pmc.ncbi.nlm.nih.gov/articles/PMC5596471/)。

当前早餐／午餐／加餐／晚餐分配为产品预设，不是经过临床验证的最佳比例：默认或恢复日 25%／32%／13%／30%；早间训练 28%／30%／12%／30%；午间训练 25%／35%／10%／30%；晚间训练 24%／30%／12%／34%。蛋白质餐次比例保持 23%／32%／15%／30%。用户可以预览调整，不保证每道菜精确命中分配。

## 当日目标与历史

`src/nutrition/timeline.ts` 在查看饮食页、档案／偏好／训练安排／时段变化时保存当天实际生成的目标快照。不会在后台替未打开应用的日期生成目标，也不会补造旧记录的历史目标。

快照保存计算结果、营养目的、饮食方式、活动水平、身体资料、计划训练及捕获时间；同样的状态不重复写入。一天最多保留 64 个快照（最初一个及最近 63 个），日期状态在加载或捕获时保留最新 1095 个日期。菜单引擎版本为 `local-menu-2`，导出格式为 `2.3-mobile`；应用发布版本没有因此改动。

历史页只显示当日已保存的目标，缺失时明确提示没有快照。当天改变目的、饮食方式或准备状态会在复盘中标识，避免混算。

最新有效体重如果进入低体重范围，自动目标暂停，即使用户尚未用该体重重新校准档案。不会仅根据一次体重记录自动改变能量目标。既有成人范围及健康筛查仍适用，参考 [NIDDK 成人体重工具范围](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner)。

## 记录完整度与周复盘

完整度是用户的明确声明，不是系统已经证明用户记录了全部饮食。修改、移动或删除摄入条目会撤销相关餐次的确认，要求重新检查；只有四餐全部确认才算全日记完。

七天状态区分：

- 无记录、未确认：缺失，不能推断为少吃。
- 有记录、未全日确认：部分记录，不用于完整日均值。
- 四餐确认：完整记录。明确确认的零摄入会保留，但不会鼓励节食或自动补偿。

完整日均值使用完整日期；与目标比较时再限定为同一批有当日就绪目标快照的日期。至少四天可比较记录、目的和饮食方式一致且当前目标就绪，才展示趋势比较。四天及偏差阈值属于谨慎的产品门槛，不是诊断标准。

本周目的变化、风险状态或样本不足时只解释限制，不自动改高／改低目标。照片估算显示不确定性，体重趋势提示先核对条件，不执行节食或运动补偿。

## 下一餐草案

`src/nutrition/adjustments.ts` 负责确定性工具：

- 只针对今天尚未记录、尚未确认完成的餐次；不覆盖已吃记录或历史日期。
- “下一餐”依据本地时段寻找合适的未完成餐次；用户也能手选具体餐次。
- 按已吃调整前，所有之前餐次和已存在记录的餐次都须明确确认记完。记录不足时提示补齐，不把漏记当成缺口。
- 只从现有真实食品和菜谱生成候选，执行饮食方式、过敏、做饭时间与预算过滤。食品库过滤不能证明外卖、品牌食品或厨房交叉接触安全。
- 按已吃调整限制单餐变化：用于匹配的能量、碳水、脂肪目标在原餐参考的 85–115%，蛋白质在 80–125%；最终候选热量在原餐的 80–120%。这些是产品安全约束，不是临床配餐处方。
- 页面明确区分“推荐菜单合计”和“已记＋余下推荐”，后者不是实际摄入；已完成或已有记录的餐次不再重复加为将来摄入。
- 草案展示原餐、建议餐、各营养差异、食材份量与限制；未确认时零写入。

确认时重新读取已接受的档案和训练写入、营养日志、当前日期、完整度和菜单版本，重新生成并比对草案。资料、记录、餐次或日期变化后拒绝过期建议；不会因为模型给出一个 recipe ID、克数或热量就直接执行。

应用仅保存该餐次覆盖项，其他餐次和摄入条目不变。手动换一道、改变菜单依据或恢复原方案会失效／移除对应覆盖项。数据库快照加载时从已知菜谱和食品重新核对营养，不信任存储中的任意数字。

## 连续问答与隐私

`NutritionAgentModal` 保存最近会话，发送最近三轮已完成问答；关闭不清空。2026-09-29 已新增确认记忆、语音记餐和原书检索，见 [助手说明](./nutrition-assistant-2026-09-29.md)。聊天不直接计入摄入，核对记餐卡并确认后才写入。长期需求不是经过临床确认的病历。

联网前明确同意发送问题、营养偏好（含过敏与风险标记）、今日训练／饮食／完整度／周复盘摘要和最近三轮问答。不上传姓名、原图或逐日完整历史；用户在提问中主动填写的信息仍会发送给服务商。照片识别有独立的上传同意流程。

助手输出最多50字的解释、有限来源和可选意图。除 `{type,slot,focus}` 菜单换餐/调整外，现支持确认后的需求记忆和实际饮食新增；不接受数值处方、任意食谱编号、已有摄入删除或自动保存。未经确认的模型建议没有写权限。

服务端对已知过敏食物提及、安全保证、治疗与极端节食、数字处方、伪造来源及“已经替你保存”等回答进行保守拒绝。不合格回答、来源和操作意图整份丢弃，返回明确标识的固定谨慎说明。词表和提示词有误拦与漏拦可能，不能声称具备临床过敏判断能力。

助手中的本地菜单快捷工具已按用户要求移除。首次联网或语音时才显示简短同意提示，没有同意不发送问题；手动记餐不受影响。服务接口、限制和费用边界见 [本地服务说明](./nutrition-service.md)。

## 持久化与异常保护

新字段继续保存在 `nutrition_journal_v1`：`trainingTime`、`days`、`mealOverrides`。旧文件正常加载为这些字段的空状态，不伪造历史；写入通过单一营养文档和序列化队列保存成功后才更新 UI。

本地营养文件不能解析、结构异常或包含无法安全加载的摄入条目时，保留原始文本并暂停所有饮食写入和自动快照。页面显示错误，导出含 `recovery.nutritionRaw` 便于人工恢复；日志不输出原始文件片段。不会用空日志覆盖坏文件。用户明确清除数据成功后才解除保护。
